== Lambda 架构大数据演进案例：广告报表写时合并优化
*业务诉求*：在一个广告报表中，同时展示 ##“外部曝光数据”##（第三方如腾讯提供，每天/每小时拉取）和##“内部转化数据”##（用户在平台下单付款，实时产生）。

*技术难点*：两类数据来源不同、时效性不同，如何在报表中完美*合并（Merge）*？

整个架构的演进，就是**“合并（Merge）操作发生的位置”**的演进。

=== 第一版：典型 Lambda 架构（当前痛点：服务层算到崩溃）
*核心逻辑*：底层拼装，把两路数据各自存好，*Java 服务层查询时在内存里做合并（读时合并）*。

*核心痛点（瓶颈）*：

1. 实时曝光缺失：第三方曝光只按天进入 MySQL，未进入实时层；实时流只处理内部 Kafka 转化消息，因此第一版无法在实时链路中提供小时级曝光，实时报表不完整。

2. 实时层缺少业务维度：Redis 只按追踪链接维度存内部转化聚合，不含广告 ID；Java 服务层虽然可以通过 MySQL 广告关系表补全广告语义，但必须每次查询都做跨源关联和二次聚合，读时合并成本高。

=== 第二版：缓解 Java 服务层压力（当前痛点：Redis 查询瓶颈）
*核心改进*：增加了一个 Python 常驻脚本，不断调用第三方 API 的小时报表，更新当日的曝光数据表（将其推入实时存储/数据库）。

第二版将曝光数据接入实时层，减轻了 Java 直接调用第三方 API 和写入曝光的压力，
但由于 Redis 仍以链接维度存储、缺少广告语义，Java 必须按广告-链接关系扇出查询 Redis_Exp 和 Redis_Tran，并在内存中二次聚合。
查询次数随“广告数 × 链接数 × 指标数”放大，所有服务实例又共享 Redis，导致 Redis 的 QPS、带宽、内存和单线程处理能力成为新的集中瓶颈。
因此第二版只是把瓶颈从写路径转移到 Redis 读路径，读时合并问题并未根治。

=== 第三版：统一大宽表 + 写时合并（服务层查询极简，写入端成为新关注点）
*核心逻辑*：在线服务层取消 Redis，只保留一张 MySQL 广告大宽表。

TIP: 对于 MySQL 数据库，大宽表的字段数需评估，若超过 50 列需考虑拆列、分区或改用列式存储引擎。

- 大宽表以 `(stday, 广告ID)` 或 `(stday, 广告ID, 追踪链接)` 为唯一键，包含曝光、点击、转化等指标。
- 把“广告与追踪链接”的关联和指标合并，从查询时提前到写入时，实现写时合并（Write-time Join）。

*写入方式*：

* 离线层：Hive/Spark 离线任务每天重算 T+1 及历史数据，按业务日期 `stday` 写入或覆盖大宽表。
* 实时层：Python 脚本小时级拉取第三方当天曝光，对 `stday = 当天` 的行做 upsert，更新曝光字段；内部实时下单/付款消息经 Spark Streaming 后调用 Java 更新接口，先将追踪链接映射为广告 ID，再对 `stday = 当天、广告ID` 的行做 upsert 或增量更新转化字段。
** 一致性：通过订单 ID/消息 ID 去重、幂等更新、批量合并、缓冲、分片和监控，避免重复计数与 MySQL 热点行锁。次日由离线任务重算并覆盖当天数据，保证最终一致。

* 服务层*：Java 查询服务只读这张大宽表，不再跨 MySQL 和 Redis 做 Join，也不在查询时做二次聚合，因此查询路径极简；但仍可能有过滤、排序、分页或轻量汇总。

**关键澄清**：`stday` 是业务日期，不是“离线/实时”的来源标记。实时链路只写 `stday = 当天`，离线链路负责 `stday ++<++= 昨天` 及历史修正。第三版解决的是服务层读时合并瓶颈，不是彻底消除所有瓶颈；写入端 MySQL 的并发、幂等、热点和吞吐成为新的关注点。

IMPORTANT: *软考考点*：写时合并（Write-time Join）、计算左移、大宽表设计、读写路径分离、查询极简，同时要说明写放大和写入端治理。

*第三版的核心魔法：写时合并（Write-time Join）*

* *统一存储*：在线服务层利用 MySQL 的 `stday` 字段区分业务日期。
    ** `stday = 当天日期`：实时链路写入当天曝光和转化，并做 upsert/增量更新。
    ** `stday ++<++= 昨天`：离线链路写入、重算或覆盖历史曝光和转化数据。
    ** 次日离线任务重算并覆盖当天数据，保证最终一致。

* *写时关联*：Spark Streaming 不再往 Redis 写，而是调用 Java 更新接口。接口内先把当前下单的追踪链接映射为广告 ID，再对 `stday = 当天` 的大宽表行做 upsert 或增量更新转化字段。

* *服务极简*：复杂的关联操作（广告与追踪链接）被分散到每条订单下单的处理过程中。
    ** 最终 Java 服务层只需要读取一张 MySQL 大宽表，不再做跨 MySQL/Redis 的 Join 和查询时二次聚合，查询路径极简；
    ** ##但写入端成为新的关注点，需要处理幂等、批量合并、分片、缓冲和监控##。

=== 给你的复习建议
在软考论文或案例分析中，如果遇到大数据架构题，**“写时合并（Write-time Join）”和“计算左移”**是绝对的高分词汇。

第三版通过“大宽表”把复杂的关联逻辑从“查询阶段”转移到了“数据写入阶段”，这正是架构设计中最经典的优化思想！

=== 实时处理过程
[discrete]
==== 1. 日志采集
在各应用系统部署采集组件 *Filebeat*，实时采集日志数据并输出到 *Kafka* 缓存。

[discrete]
==== 2. 日志清洗与解析
基于大数据计算集群的 *Flink* 计算框架，实时读取 *Kafka* 中的日志数据进行清洗和解析，提取日志关键内容并转换成指标，以及对指标进行二次加工形成衍生指标。

[discrete]
==== 3. 日志存储
将解析后的日志数据分类存储于 *Elastic-Search* 日志库中，各类基于日志的指标存储于 *OpenTSDB* 指标库中，供前端组件搜索与查询。

[discrete]
==== 4. 日志监控
通过单独的告警消息队列来保持监控消息的有序管理与实时推送。

[discrete]
==== 5. 日志应用
在充分考虑日志搜索专业需求的基础上，平台支持搜索栏常用语句保存，选择日志变量自动形成搜索表达式，以及快速按时间排序过滤、查看日志上下文等功能。

同时，基于可视化分析和全息场景监控可实时展现各种指标和趋势，并在预警中心查看各类告警的优先级和详细信息，进而结合告警信息关联查询系统日志内容来分析解决问题。

此外，开发配置中心还提供了自定义日志解析开发功能，并支持告警规则、告警渠道配置。

== Lambda 和 Kappa 大数据架构对比
核心判断：*架构选择不是“Lambda 比 Kappa 好”或反之，而是由数据形态、时效要求、历史修正需求、合并复杂度和运维成本共同决定。*

* *广告报表系统*：数据源异构、批流并存、需要历史重算与最终一致，所以采用 *Lambda 架构思想*，并在第三版通过“大宽表 + 写时合并”优化服务层。
* *证券公司实时日志分析平台*：数据源同质、天然是事件流、要求实时解析/告警/检索，所以采用 *Kappa 架构*，用 Flink 统一处理全部数据。

=== 一、广告报表系统为什么选择 Lambda？
广告报表的业务本质是：*外部曝光数据 + 内部转化数据，在同一个报表中合并展示。*

它的数据特征决定了很难用纯 Kappa 解决：

[cols=",,,",options="header",]
|===
|数据 |来源 |时效 |接入方式
|外部曝光/点击 |第三方如腾讯 |日级/小时级 |API 定时拉取
|内部转化 |平台下单付款 |实时 |Kafka 实时消息
|历史数据 |Hive/日志 |T+1/历史 |离线批处理
|===

[discrete]
==== 1. 批流数据源天然分离

第三方曝光数据不是实时消息流，而是按天或按小时拉取的报表数据；内部转化则是 Kafka 实时下单/付款消息。 +
这两类数据**来源不同、时效不同、语义不同**，所以需要：

* *批处理层*：处理第三方日级/历史曝光，以及内部浏览/下单日志的 T+1 重算。
* *速度层*：处理当天实时转化，以及 Python 脚本小时级拉取的当天曝光。
* *服务层*：对外提供统一报表查询。

这正是 Lambda 的典型分层：*Batch Layer + Speed Layer + Serving Layer*。

[discrete]
==== 2. 需要历史重算和最终一致

广告报表中，`stday` 是业务日期，不是“离线/实时”来源标记。 +
实时链路只写 `stday = 当天`，离线链路负责 `stday <= 昨天` 及历史修正。 +
次日离线任务重算并覆盖当天数据，保证最终一致。

这种“当天实时增量 + 次日离线覆盖修正”的模式，非常适合 Lambda： - 实时层保证当天可看； - 批处理层保证历史准确、可重算； - 服务层统一查询。

如果强行用 Kappa，就要假设第三方曝光也能实时流式接入，并且 Kafka 能长期保存所有历史消息、支持全量重放。但案例中第三方只提供日/小时报表，历史全量重算和外部数据修正在批处理中更自然。

[discrete]
==== 3. 合并复杂，需要“计算左移”

第一版是典型 Lambda，但 Java 服务层做**读时合并**，查 MySQL、Redis 后在内存里聚合，导致服务层崩溃。 +
第二版把曝光接入实时层，但 Redis 仍按链接维度存储，Java 仍需按广告-链接关系扇出查询，Redis 成为瓶颈。 +
第三版用 *MySQL 大宽表 + 写时合并*，把“广告与追踪链接”的关联从查询时提前到写入时。

注意：第三版虽然服务层只读一张大宽表，但底层仍有： - 离线层：Hive/Spark 每天重算 T+1 及历史； - 实时层：Python 脚本和 Spark Streaming 更新当天数据。

所以它仍然是 *Lambda 架构的演进*，不是 Kappa。它解决的是服务层读时合并瓶颈，而不是取消批处理层。

=== 二、证券公司实时日志平台为什么选择 Kappa？
该平台的核心是：*多源日志实时采集、清洗、解析、指标提取、存储、搜索和告警。*

它的数据特征非常统一：

* 各源系统通过 Filebeat 采集日志；
* 日志进入 Kafka 缓存；
* Flink 实时读取 Kafka，清洗解析；
* 解析后的日志写 ElasticSearch；
* 指标写 OpenTSDB；
* 告警通过独立消息队列实时推送。

[discrete]
==== 1. 数据天然是事件流

日志本身就是持续产生的事件流。 +
Filebeat -> Kafka -> Flink -> ES/OpenTSDB 这条链路，天然适合流处理。 +
不需要先落一套批处理层，再单独做一套速度层。

[discrete]
==== 2. 实时性要求高

日志智能搜索、可视化图表、告警中心、数据监控都要求低延迟。 +
如果采用 Lambda，批处理层通常 T+1 或小时级，实时告警会延迟；而 Kappa 用 Flink 统一实时处理，可以更快产出指标和告警。

[discrete]
==== 3. 处理逻辑可以统一

日志采集后的清洗、解析、指标提取、二次加工、告警规则，都可以用同一套 Flink 作业或同一套流处理逻辑完成。 +
这避免了 Lambda 中常见的： - 批处理和流处理两套代码； - 两套指标口径不一致； - 两套运维链路； - 结果对不齐。

[discrete]
==== 4. 历史查询不依赖独立批处理层

日志平台的历史查询主要面向 ElasticSearch 和 OpenTSDB。 +
如果需要重算，Kappa 也可以通过 Kafka 重放历史消息，用同一套 Flink 逻辑重新计算。 +
它不像广告报表那样，必须每天用离线任务全量重算历史并覆盖修正外部曝光数据。

所以证券公司日志平台选择 Kappa，是因为： - 数据源同质，都是日志事件流； - 实时性要求高； - 处理逻辑可统一； - 存储层分工明确：ES 做日志检索，OpenTSDB 做指标； - 运维一套 Flink 引擎即可，架构更简单。

=== 三、对比总结

|===
|维度 |广告报表系统 |证券公司日志平台
|架构选择 |Lambda 思想，第三版写时合并 |Kappa 架构
|数据源 |第三方曝光 + 内部转化，异构 |多源日志，同质事件流
|时效 |日级、小时级、实时混合 |实时流处理
|历史处理 |离线 Hive/Spark 每天重算、覆盖 |Kafka 重放或 ES/OpenTSDB 查询
|合并复杂度 |高，广告 ID、追踪链接、曝光、转化需关联 |相对统一，解析、指标、告警

=== 一句话总结
* *广告报表选 Lambda*：因为它是“异构数据源 + 批流分层 + 历史重算 + 复杂合并”的场景，Lambda 的批处理层和速度层能分别解决历史准确性和当天实时性。

* *证券日志选 Kappa*：因为它是“同质事件流 + 实时处理 + 统一逻辑 + 低延迟告警”的场景，Kappa 用 Flink 一套引擎处理全部数据，架构更简洁、时效更高。

软考中可用的关键词：

- Lambda：批处理层、速度层、服务层、读时合并、写时合并、计算左移、大宽表、最终一致。
- Kappa：一切皆流、Kafka 重放、Flink 统一处理、流批一体、实时日志分析、低延迟告警。

== Lambda 和 Kappa 高频词
Lambda 和 Kappa 是软考大数据架构题里的高频词。答题时不要只写名词，要能串成“架构逻辑”。

=== 一、Lambda 架构关键词
*Lambda 架构核心：批处理层 + 速度层 + 服务层，批层保准确，速度层保实时，服务层合并查询。*

[arabic]
. *批处理层*
* 存储全量原始数据，周期性离线重算。
* 优点：数据准确、可重放、吞吐大。
* 缺点：延迟高，不适合秒级响应。
* 软考表述：批处理层负责全量计算，生成批视图，保证最终准确性。

. *速度层*
* 处理实时增量数据，做近似或增量计算。
* 优点：低延迟，能快速看到最新结果。
* 缺点：可能不完整、不准确，需要批处理层修正。
* 软考表述：速度层负责实时计算，生成实时视图，弥补批处理层延迟。

. *服务层*
* 存放批视图和实时视图，对外提供查询。
* 常见组件：HBase、Elasticsearch、Redis、ClickHouse 等。
* 软考表述：服务层负责合并查询结果，提供统一数据服务。

. *读时合并*
* 查询时把“批处理层结果”和“速度层结果”合并。
* 优点：写入简单，批处理重算不影响实时层。
* 缺点：查询复杂、延迟高、服务层压力大。
* Lambda 经典做法就是读时合并。

. *写时合并*
* 在写入服务层时就把批结果和实时结果合并好。
* 优点：查询快，直接读结果。
* 缺点：写入复杂，批处理重算时更新代价高。
* 可理解为：用写入成本换查询性能。

. *计算左移*
* 把计算尽量提前到数据产生、接入或流处理阶段。
* 目的：减少下游批处理压力和查询时计算量。
* Lambda 中速度层就是计算左移；Kappa 是更彻底的计算左移。

. *大宽表*
* 把事实数据和维度字段冗余、预关联到一张宽表中。
* 目的：避免查询时 join，提高查询性能。
* 常用于服务层，但会有数据冗余和一致性维护成本。

. *最终一致*
* 实时结果可能短暂不准确，批处理层定时重算后修正。
* 系统不是强一致，而是经过一段时间后达到一致。
* 软考表述：Lambda 通过批处理层修正速度层，实现最终一致。

*Lambda 答题串联：* > Lambda 采用批处理层保证全量准确，速度层保证实时低延迟，服务层通过读时合并或写时合并对外服务；通过计算左移和大宽表优化查询，系统整体最终一致。

=== 二、Kappa 架构关键词
*Kappa 核心：一切皆流，用流处理统一实时和历史，去掉 Lambda 的批处理层。*

[arabic]
. *一切皆流*
* 认为批数据只是“有界流”，实时数据是“无界流”。
* 所有数据都可用流处理方式处理。
* 软考表述：Kappa 将批视为流的特例，统一用流处理引擎计算。

. *Kafka 重放*
* Kafka 持久化存储消息，可按 offset 重新消费历史数据。
* 需要重算时，从 Kafka 重放数据，而不是跑离线批处理。
* 优点：架构统一；缺点：依赖 Kafka 保留周期和重放成本。

. *Flink 统一处理*
* 用 Flink 同时处理实时流和历史批数据。
* 支持状态管理、窗口、Checkpoint、Exactly-once。
* 软考表述：Flink 提供流批一体能力，一套代码处理实时与历史数据。

. *流批一体*
* 流处理和批处理用同一套引擎、同一套 API、同一套代码。
* 避免 Lambda 中维护批层和速度层两套链路。
* 优点：架构简单、开发运维成本低。
* 缺点：对消息队列留存、流处理能力要求高。

. *实时日志分析*
* 典型链路：日志采集 → Kafka → Flink → Elasticsearch/ClickHouse → 看板。
* 适合 Kappa：日志天然是流，实时解析、聚合、统计。
* 软考表述：Kappa 常用于实时日志分析场景。

. *低延迟告警*
* 流处理逐条或按窗口计算，秒级发现异常。
* 可结合 Flink CEP、规则引擎、阈值判断。
* 软考表述：Kappa 通过流计算实现低延迟告警和实时监控。

*Kappa 答题串联：* > Kappa 主张一切皆流，基于 Kafka 重放历史数据，使用 Flink 统一处理，实现流批一体；适合实时日志分析、低延迟告警等场景。

=== 三、Lambda 与 Kappa 对比记忆
[width="100%",cols="34%,33%,33%",options="header",]
|===
|维度 |Lambda |Kappa
|核心思想 |批处理 + 流处理两套链路 |一切皆流，一套流处理
|关键层 |批处理层、速度层、服务层 |流处理层、服务层
|准确性 |批处理层保证准确 |依赖流处理重放和状态
|实时性 |速度层低延迟 |全链路低延迟
|合并方式 |经典读时合并，也可写时合并 |持续写入结果，偏写时合并/物化
|典型组件 |Hadoop、Spark、Storm、HBase |Kafka、Flink、ClickHouse
|适用场景 |既要实时又要离线准确 |实时日志、低延迟告警、流批一体
|缺点 |架构复杂，两套链路维护成本高 |依赖消息重放，复杂批处理较弱
|===

=== 四、软考答题模板
*问 Lambda：* > Lambda 架构分为批处理层、速度层和服务层。批处理层全量重算保证准确性，速度层实时计算保证低延迟，服务层通过读时合并或写时合并提供查询。通过计算左移、大宽表优化性能，系统最终一致。

*问 Kappa：* > Kappa 架构主张一切皆流，批数据视为有界流。基于 Kafka 重放历史数据，使用 Flink 统一处理，实现流批一体，适合实时日志分析和低延迟告警。

背这几个词时，重点记：*Lambda = 三层 + 合并 + 最终一致；Kappa = 一切皆流 + Kafka 重放 + Flink 流批一体。*
